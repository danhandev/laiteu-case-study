# 02. 커뮤니티 피드 조회 — 인덱스 스캔 문서 1,777건 → 30건

> 측정 조건: EC2 m6g.medium, MongoDB, k6 부하테스트(VU 8 → 40).
> 측정 도구: k6, MongoDB `explain("executionStats")`.

## 문제

커뮤니티 피드가 "느린 것 같다"는 인상은 있었지만 근거가 없었습니다. 먼저 목표치를
역산했습니다.

```
DAU 1,000명 × 세션당 요청 15건 ÷ 86,400초 × 피크 계수
→ 목표 Peak TPS ≈ 1.3
```

이 목표를 기준으로 k6 시나리오를 Smoke / Load / Stress / Spike 4단계로 설계해
`docs/performance/`에 두고 측정했습니다.

| 엔드포인트 | p95 | RPS |
|---|---|---|
| community-feed | 7.31s | 3.86 |
| tags-filter | 7.49s | 3.86 |

목표 TPS 1.3을 넘기긴 했지만 p95가 7초대라, 트래픽이 조금만 늘어도 무너지는 상태였습니다.

## 원인

`explain("executionStats")`를 떠서 두 가지를 확인했습니다.

**1. 인메모리 SORT 발생.** 기존 인덱스가 `(roles, createdAt, ...)` 순서였는데,
`roles`는 **배열 필드**입니다. 배열 필드가 중간에 낀 복합 인덱스는 뒤따르는 키의
정렬 순서를 보장하지 못해, MongoDB가 인덱스로 정렬을 처리하지 못하고
`SORT` 스테이지를 메모리에서 수행하고 있었습니다.

**2. 정렬 기준별 전체 fetch.** `favoritesCount` 기준 정렬 시 조건에 맞는 615건을
전부 가져와 메모리에서 정렬한 뒤 페이지를 잘랐습니다.

```
executionStats
  totalDocsExamined: 1,777
  stage: SORT (in-memory)      ← 인덱스로 처리되지 않음
```

## 해결

정렬 기준이 세 가지(최신순 · 인기순 · 태그 필터)라 하나의 인덱스로 모두 커버할 수
없었습니다. **정렬 기준별로 복합 인덱스를 3종 설계**하고, 각각 ESR(Equality → Sort → Range)
순서를 지켜 배열 필드가 정렬 키 앞에 오지 않도록 배치했습니다.

- 인덱스 A — 최신순 피드: `(status, createdAt)`
- 인덱스 B — 인기순 피드: `(status, favoritesCount, createdAt)`
- 인덱스 C — 태그 필터: `(status, tags, createdAt)` (배열 필드를 마지막 equality 위치로)

## 결과

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 인덱스 스캔 문서 수 | 1,777건 | **30건** (98% ↓) |
| SORT 스테이지 | 인메모리 SORT 발생 | 인덱스로 처리, 스테이지 제거 |

## 배운 것

- **복합 인덱스에서 배열 필드의 위치가 정렬 가능 여부를 좌우한다.** 필드 순서를 바꾸는 것만으로
  인메모리 SORT가 사라졌습니다. 인덱스는 "걸었다/안 걸었다"가 아니라 "어떤 순서로 걸었는가"의
  문제였습니다.
- **정렬 기준이 여러 개면 인덱스도 여러 개 필요하다.** 하나로 다 커버하려다 어느 쪽도
  못 쓰는 인덱스가 되는 것보다, 쓰기 비용을 감수하고 정렬별로 나누는 편이 나았습니다.
  이 서비스는 읽기 비중이 압도적이라 이 교환이 유리했습니다.
- **부하테스트 목표치는 감이 아니라 역산으로 정한다.** DAU와 세션당 요청 수에서 Peak TPS를
  뽑아두니, 측정 결과를 "빠르다/느리다"가 아니라 "목표 대비 여유가 얼마"로 말할 수 있었고
  서버 증설 우선순위도 그 근거로 정했습니다.
