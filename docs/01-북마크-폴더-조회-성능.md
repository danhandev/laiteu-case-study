# 01. 북마크 폴더 조회 API — 7,031ms → 138ms

> 측정 조건: 폴더 1개에 북마크 항목 767건, 페이지 크기 20, EC2 m6g.medium, MongoDB.
> 측정 도구: Spring `StopWatch`(단계별), MongoDB `explain("executionStats")`.

## 문제

모니터링에서 `GET /favorites/folders/{folderId}`의 p95가 **7,031ms**로 찍혔습니다.
화면에는 20건만 보여주는 페이지 단위 조회인데 7초가 걸린다는 건, 어딘가에서 20건보다
훨씬 많은 일을 하고 있다는 뜻이었습니다.

데이터 구조는 폴더 도큐먼트 안에 북마크 항목이 배열로 들어가는 embedded document입니다.

```java
@Document
public class FavoriteFolder {
    private String id;
    private String ownerId;
    private List<FavoriteArtworkEntry>    artworkEntries;     // 767건
    private List<FavoriteJobPostingEntry> jobPostingEntries;
}
```

## 원인 추적

가설부터 세우지 않고 `StopWatch`를 도메인 서비스 안쪽에 박았습니다. 컨트롤러나 ORM 경계에
박으면 DB 시간과 비즈니스 로직 시간이 섞여서, 정작 비싼 짓을 하는 도메인 코드의 분기가
보이지 않습니다.

```
StopWatch 'getFavoriteFolderContents': total = 7,031ms
00093ms  01%   folder fetch
00420ms  06%   batch queries (total=767)
00024ms  00%   page batch queries (page=20)
06494ms  93%   build summaries      ← 단순 DTO 변환 단계가 6.5초
```

메모리에서 객체를 매핑만 하는 단계가 6.5초일 리가 없었습니다. 코드를 되짚어보니
썸네일 폴백 분기가 있었습니다.

```java
if (artwork.getThumbnailImage() != null) {
    thumbnailUrl = artwork.getThumbnailImage().getPreviewImageUri();
} else {
    // 레거시 데이터 폴백 — 여기서 한 건씩 조회
    ArtworkImage img = artworkImageRepository.findById(artwork.getRepresentativeImageId())...
}
```

평상시에는 `thumbnailImage`가 채워져 있어 추가 쿼리가 없습니다. 그런데 **레거시 데이터
일부는 이 필드가 null**이었고, 767건 중 절반 이상이 폴백 경로를 타면서 한 건씩 쿼리를
던지고 있었습니다. 표준적인 N+1 패턴(연관관계 지연 로딩) 밖에 숨어 있어서 코드 리뷰로는
잡히지 않던 종류였습니다.

## 해결 — 3단계

### 1단계. 폴백 경로를 배치 조회로 (7,031ms → 968ms)

폴백이 필요한 `representativeImageId`를 먼저 모아 `findAllById`로 한 번에 조회하고,
매핑 단계에서는 메모리 맵만 조회하도록 바꿨습니다.

### 2단계. 전체 fetch를 projection + 페이지 단위로 분리 (968ms → 396ms)

남은 시간을 다시 재보니, 페이지는 20건인데 767건을 **전부 전체 필드로** 가져와서
메모리에서 자르고 있었습니다. 3단계로 쪼갰습니다.

1. 활성 여부 판단에 필요한 필드(`publicId`, `status`)만 projection으로 조회
2. 메모리에서 필터 · 정렬 · 페이징
3. 페이지 분량(20건)만 전체 필드로 조회

### 3단계. Covered Query (396ms → 138ms)

2단계의 projection 조회가 여전히 문서를 읽고 있었습니다. `(publicId, artworkStatus)`
복합 인덱스를 **ESR(Equality → Sort → Range)** 순서에 맞춰 설계해, 인덱스만 읽고
문서를 읽지 않는 covered query로 만들었습니다.

```
explain("executionStats")
  totalDocsExamined: 0     ← 문서 접근 0건
  totalKeysExamined: 767
```

## 결과

| 단계 | 응답 시간 | 개선 |
|---|---|---|
| 개선 전 | 7,031ms | — |
| 1단계 (배치 조회) | 968ms | 86% ↓ |
| 2단계 (projection + 페이지 분리) | 396ms | 94% ↓ |
| 3단계 (covered query) | **138ms** | **98% ↓** |

## 배운 것

- **성능 문제는 한 군데서 크게 새지 않고, 여러 군데서 조금씩 샌다.** 1단계만 하고 멈췄다면
  968ms에서 끝났을 것입니다. 한 단계 고칠 때마다 다시 측정한 것이 나머지 두 병목을 드러냈습니다.
- **N+1은 연관관계에만 있는 게 아니다.** 이 사례의 원인은 레거시 데이터 폴백 분기였고,
  평상시 트래픽에서는 재현되지 않았습니다. 데이터 상태에 따라 분기하는 코드는
  "그 분기를 타는 데이터가 얼마나 되는가"를 함께 봐야 합니다.
- 캐싱이나 서버 증설 없이 끝났습니다. 측정 → 가장 비싼 곳 제거 → 재측정의 반복으로 충분했습니다.

> 같은 API를 다른 시점(폴더 747건 기준)에 측정했을 때는 28,279ms → 263ms로 개선한 이력도
> 있습니다. 한 번에 끝난 작업이 아니라 여러 차례에 걸쳐 반복 개선했습니다.
